# 测过什么，没测过什么

## 先说结论

**能注入，也跑通过一次真实 Codex CLI 请求；还不能承诺默认配置交给群友就能用。**

2026-09-18 的真实联调发现，上游返回的 state 是 11 块，默认基线却是 10 块。默认配置因此拒绝了它，Codex 收到 `503 state_unavailable`。临时把独立测试配置改为接受 11 块后，程序采集并注入了这份 state，真实 Astra 返回完成事件，Codex CLI 显示 `OK` 并正常退出。

这是两件不同的事：转发和注入链路成立了，但默认筛选规则在这个出口上没有找到符合条件的值。**正式默认值仍为 10，没有为了让测试变绿就改成 11。** 当前不建议当作免调试的稳定版批量分发。

## 真实 Astra 联调

环境为 macOS / Apple Silicon、Codex CLI `0.154.0`。测试使用独立 Codex 目录，由 Go 服务自动配置 provider，CLI 不复用日常配置、项目规则或会话。客户端运行在限制写入目录与网络出口的 macOS 沙盒中。

链路为：

```text
真实 Codex CLI → Go 服务 → 本地计数转发器 → 真实 Astra 上游
```

计数转发器只用于验收：最多放行 3 次模型请求，不修改请求 state，不替服务采集，也不重试。它记录是否注入、state 长度与指纹、HTTP 状态和完成事件，不记录认证值或正文。这个测试没有验证真实订阅节点。

| 次数 | 用途 | 结果 |
|---|---|---|
| 1 | 默认 10 块基线下采集 | 上游 HTTP 200，返回 11 块 / 312 字符 state，SSE 完成；服务拒绝该候选，没有转发正式问题 |
| 2 | 独立测试配置临时接受 11 块，再采集 | 上游 HTTP 200，候选被接受 |
| 3 | CLI 正式请求，经服务注入刚采集的 state | 注入指纹与第 2 次采集一致，上游 HTTP 200、SSE 完成；CLI 输出 `OK`，退出码 0 |

第 3 次响应没有再次附带 state 头；服务保留当前值，没有把缺少响应头当成新状态或直接清空它。总计正好 3 次模型请求，之后停止，没有继续探测。

测试结束后，日常 Codex 的配置和登录文件哈希均未改变；测试配置已恢复，复制到测试目录的临时凭据已删除。没有刷新登录、使用重置卡或切换系统代理。

这次只证明 **CLI 接到了本地 provider、服务确实注入、真实上游能完成回复**。不能据此证明 10 块优于 11 块，也不能证明降智或限流得到改善。桌面端完整使用、Windows 实际 Codex 联调和长会话，还需要继续验证。

## 遇到同样的 503 怎么看

先看日志里的 `probe_finished`：

- `status: 200`、`result: "shape_mismatch"`：请求成功了，但 `state_blocks` 与 `expected_blocks` 不符。本次实测就是 11 对 10。
- `result: "state_time_rejected"`：封装可读，但时间不符合本地规则。
- `result: "request_failed"`：请求、封装解析或 SSE 完成检查失败；结合 HTTP 状态与网络情况排查。

日志只增加这些诊断数字和固定结果名，不输出完整 state。不要仅为了消掉报错，就把基线改成刚看到的数字——那会改变筛选方法，不代表解决了原来的问题。

## 本地验收

初始版本在 2026-09-18 完成本地隔离测试，使用 macOS / Apple Silicon 和 Go 1.27.1。测试使用临时目录、合成凭据和本地模拟服务器，没有接入日常 Codex 配置、真实订阅或模型账号。

这里的“隔离”是路径与测试上游隔离，不是虚拟机或完整操作系统沙盒。

| 检查 | 内容 |
|---|---|
| `go test -race -count=1 ./...` | 全包测试与竞态检查 |
| `go vet ./...` | 静态检查 |
| state fuzz | 随机输入解析测试，10 秒运行约 160 万次，没有发现崩溃 |
| 配置事务 | 注释保留、根配置注入、精确恢复、用户中途修改、符号链接保护 |
| 真进程恢复 | 启动子进程、单实例锁、强制结束，再由 CLI 恢复配置 |
| 请求转发 | 单次快照、认证隔离、正文和会话链保留、SSE 即时返回、取消传播 |
| 失败处理 | 401/403 停止该凭据继续采集、429 冷却、Retry-After、形状异常不重放生成请求 |
| 代理 | 本地 HTTP CONNECT 和 SOCKS5 用户名密码握手、目标域名与隧道数据 |
| 订阅 | YAML、URI、Base64、大小限制、无效项拒绝、危险字段拒绝、环境变量来源 |
| 日志 | 私密内容不进入常规日志、轮换数量有上限 |
| 交叉构建 | Windows amd64/arm64、macOS amd64/arm64 |

SS、VMess、VLESS、Trojan、Hysteria2 还覆盖了解析和核心适配器构造。这不等于这些协议已经连接过真实节点。SSR、Hysteria、TUIC 的协议实现来自 Mihomo，尚未在本项目中做对应的实际节点联调。

依赖检查使用 `govulncheck`。本地修复后没有检测到调用路径可达的已知漏洞；工具仍提示 3 项依赖模块层面的漏洞，但未发现代码调用路径。这个结果有时效，发新版本前需要重跑，不能理解为没有任何安全风险。

## Windows 和其他系统

提交 `0c99354` 的 [CI](https://github.com/gylive/ccodex-sleep-state/actions/runs/35328192826) 已在 Windows、macOS、Linux 三个 runner 上通过 `go vet`、全包竞态测试和构建。这比只做交叉编译多了一层实际系统运行检查，但**不代替 Windows 桌面上的 Codex 真实联调**。后续提交以 [Actions](https://github.com/gylive/ccodex-sleep-state/actions) 的对应结果为准。

Windows ARM64 和 Intel Mac 的应用包由交叉编译产生，没有各自的完整桌面环境联调。

## 还需要实际使用验证的部分

- 桌面客户端是否完整采用自定义 provider，以及项目/任务配置是否覆盖它。CLI 的一次成功不代表桌面端全部功能都已覆盖。
- 不同出口能否稳定采到默认基线的 state，以及这个基线是否仍有实际价值。
- 某个账号、代理或地区在实际使用中有没有改善降智和请求受限。
- 长会话的上下文连续性、上游密文轮换和各类服务商节点参数。

这些问题不能用模拟服务器证明。部署后可以从少量请求开始，保留原配置作为对照，观察实际回答和失败情况；不要仅凭 state 长度给结果打分。
